# Практичне заняття 9. Генеративні шаблони в деревовидній структурі

Як деревовидну систему обрано представлення структурованого тексту (`core/text`).
Корінь — `Root`, контейнери — `Heading`, листки — `Paragraph`, `Link`, `Image`.

Впроваджено чотири генеративні шаблони: **Абстрактна фабрика**, **Будівник**,
**Прототип** і **Сінглтон**. Пояснення також є в docstring-ах відповідних модулів.

---

## 1. Абстрактна фабрика — `core/text/families.py`, `core/text/variants.py`

**Що.** `TextElementFactory` оголошує по одному методу створення на кожну роль елемента:
`create_root`, `create_heading`, `create_paragraph`, `create_link`, `create_image`.
Три конкретні фабрики створюють по одній «родині» елементів:

| Фабрика | Формат | Приклад посилання |
|---|---|---|
| `PlainTextElementFactory` | чистий текст (як і раніше) | `Docs (https://...)` |
| `MarkdownElementFactory` | Markdown | `[Docs](https://...)` |
| `HtmlElementFactory` | HTML (з екрануванням) | `<p><a href="https://...">Docs</a></p>` |

Елементи Markdown/HTML (`variants.py`) — підкласи відповідних plain-елементів, які
перевизначають лише `render()`. Тому навігація, зміст, серіалізація й клонування
працюють з ними без змін.

**Де використовується.**
- `TextFactory` (enum + лямбди з практичної про SOLID) тепер створює елементи через
  отриману фабрику, а не через конструктори конкретних класів. За замовчуванням — plain,
  тож увесь старий код працює як раніше.
- `DocumentBuilder` і `CharacterSheetBuilder` приймають фабрику: ті самі кроки
  побудови дають документ у будь-якому форматі.
- `DocumentConverter` (`prototypes.py`) перебудовує готовий документ в іншому форматі.
- CLI: `print --format html|markdown|plain`, `sheet <id> --format html`.

**Чому.** У методичці зазначено, що система має підтримувати різні представлення (HTML, TeX).
Без фабрики довелося б або розкидати `if format == ...` по всіх `render()`, або
код, що будує документ, мав би знати конкретні класи кожного формату. З фабрикою:
- документ гарантовано складається з елементів одного формату — HTML-заголовок не отримає
  plain-параграф;
- новий формат (наприклад, LaTeX) = нова фабрика + її класи елементів; код, що будує
  документи, і всі команди не змінюються (Open/Closed).

## 2. Сінглтон — `core/text/singleton.py`

**Що.** Метаклас `SingletonMeta`: перший виклик класу створює екземпляр, наступні
повертають той самий. Потокобезпечний (блокування з подвійною перевіркою). Кожен клас
має власний екземпляр, тож `HtmlElementFactory() is HtmlElementFactory()`, але
`HtmlElementFactory() is not PlainTextElementFactory()`.

**Де.** Метаклас абстрактної фабрики `TextElementFactory`, тобто всі конкретні фабрики.
`factory_for("html")` завжди повертає один і той самий об'єкт.

**Чому саме тут, а не для кореня.** У методичці запропоновано зробити сінглтоном `Root`.
Я свідомо цього не робив: у програмі одночасно існують кілька документів — документ
користувача в текстовому режимі, листи персонажів (`sheet`), документ після `load`,
копії при конвертації у формат. Єдиний корінь на процес зламав би все це, а тести
перестали б бути незалежними одне від одного. Натомість фабрики не мають жодного стану,
і кілька екземплярів однієї фабрики не мають сенсу — це класичний випадок для
сінглтона (GoF прямо зазначає, що конкретні фабрики зазвичай реалізують як сінглтони).

## 3. Будівник — `core/text/builder.py`

**Що.** `DocumentBuilder` з «fluent» API та стеком відкритих розділів:

```python
doc = (DocumentBuilder(HtmlElementFactory())
       .heading("Intro")            # відкриває розділ
           .paragraph("Text")       # потрапляє всередину "Intro"
           .heading("Details")      # рівень 2 визначається автоматично
               .link("Docs", "https://...")
           .end()                   # назад до "Intro"
       .end()
       .build())
```

Будівник сам відстежує поточного «батька» та рівні заголовків, не дає викликати `end()`
на корені та перевикористати себе після `build()`.

**Де.** `services/character_sheet.py` — лист персонажа тепер описаний кроками будівника
замість ручного «створити заголовок → приєднати → запам'ятати → додати дітей».

**Чому.** Заголовки — композити, тому зібрати складне дерево вручну громіздко й легко
помилитися (приєднати елемент не до того батька, переплутати рівні). Будівник відокремлює
процес побудови від представлення: разом з абстрактною фабрикою ті самі кроки дають
документ будь-якого формату.

## 4. Прототип — `core/text/elements.py` (`clone`), `core/text/prototypes.py`

**Що.** Кожен елемент має `clone()` — глибоку копію себе та всього піддерева, того самого
конкретного класу (HTML-заголовок клонується в HTML-заголовок). Копія від'єднана від
дерева (`parent is None`) і не має спільного стану з оригіналом: моделі даних копіюються,
дочірні елементи клонуються. `PrototypeRegistry` зберігає іменовані шаблони й видає їх
нові копії.

**Де.**
- CLI: `cp <елемент>` — дублює елемент з усім вмістом одразу після оригіналу.
- CLI: `template save <ім'я> <елемент>`, `template use <ім'я>`, `template ls` — шаблони
  розділів (наприклад, стандартний розділ «Контакти» з посиланнями).
- `DocumentBuilder.append()` — вставка готового елемента, наприклад клона шаблону.

**Чому.** Як зазначено в методичці, з абстрактною фабрикою легко прийти до окремої
фабрики на кожен однотипний складний елемент. Прототип це замінює: однаковий розділ
налаштовується один раз і далі клонується. Код, що копіює, не знає ні конкретного класу,
ні формату, ні того, як цей розділ складався.

## Тести

`tests/test_creational_patterns.py` та `tests/test_patterns_cli.py` — 45 нових тестів:
- єдиність фабрик (зокрема при одночасному створенні з 20 потоків);
- що кожна фабрика видає елементи своєї родини, рендер у трьох форматах, HTML-екранування;
- будівник: вкладеність, рівні, помилки (`end()` на корені, повторне використання після `build()`);
- прототип: глибина й незалежність копії, збереження формату, реєстр шаблонів;
- конвертер не змінює оригінал;
- нові команди CLI.

Старі тести (134) пройшли без змін, тобто вся попередня поведінка збережена.
Разом 179 тестів, запуск: `python3 -m pytest -v`.
