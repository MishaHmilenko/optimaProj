# Практичне заняття 11. Поведінкові шаблони

Рефакторинг проєкту з першого модуля (гра + структурований текст). Впроваджено шість
поведінкових шаблонів, мінімум за завданням — чотири. Кожен або замінює вже наявний
незграбний код (дублювання, ланцюжки `isinstance`, кілька рекурсивних обходів), або дає
нову потрібну можливість: скасування ходу, статистику бою.

**Це рефакторинг:** публічні API не змінювалися, жоден старий тестовий файл не змінено.
Усі 179 попередніх тестів проходять, плюс 32 нові — разом **211**.
Детальні коментарі є в docstring-ах відповідних модулів.

| Шаблон | Де | Що замінив / що дав |
|---|---|---|
| Template Method | `core/game/abilities.py` | дублювання в `use()` кожної здібності |
| Memento | `core/game/character.py` | знімки стану персонажа без порушення інкапсуляції |
| Command | `core/game/commands.py`, `game.py` | дії стали об'єктами → історія та `undo` |
| Observer | `core/game/events.py`, `game.py` | прямий виклик displayer-а з `Game` → підписники (вивід, статистика) |
| Iterator | `core/text/iterators.py`, `ContainerElement.walk()` | три окремі рекурсивні обходи дерева |
| Visitor | `core/text/visitor.py` + серіалізація, конвертер, навігатор | ланцюжки `if isinstance(...)` |

Шаблони, які вже були в проєкті раніше і лишилися як є: `Game` — **Mediator** між персонажами;
`parse_line` + `CommandRegistry` у CLI (з практичного 13 — `ArgsParser` + `Command`/`ICommandStrategy`, див. DESIGN.md) — по суті **Interpreter** і **Command** для текстових команд.

## Гра

### Template Method — `Ability.use()`
Раніше кожна здібність у своєму `use()` повторювала перевірку цілі, вибір отримувача й
загортання результату в `AbilityResult`. Тепер `use()` — незмінний алгоритм у базовому класі:

1. перевірити ціль (якщо `requires_target`);
2. обрати отримувача (ціль або сам користувач);
3. `_apply()` — застосувати ефект *(перевизначається)*;
4. `_describe()` — описати результат *(перевизначається; є стандартний варіант для урону)*.

`PowerStrike` і `TalentAbility` тепер реалізують лише `_apply`. Тест перевіряє, що жоден
підклас не перевизначає сам `use()`, і показує нову здібність, написану лише через два хуки.

### Memento — `CharacterMemento`, `Character.save_state() / restore_state()`
Знімок усього, що може змінити дія: стати (копія моделі даних), відомі здібності, екіпіровка,
прапорець захисту. У знімка немає жодного публічного атрибута чи методу (`__slots__`, лише
`_`-поля). Читати його вміє тільки `Character` (originator), а команда (caretaker) лише зберігає.

### Command — `GameCommand` та `AttackCommand`, `HealCommand`, `UseAbilityCommand`, `EquipCommand`
Кожна дія — об'єкт з усім потрібним для виконання. `execute()` спершу бере знімки (Memento)
усіх персонажів, яких дія зачепить, а потім виконує її. `undo()` відновлює знімки. Якщо дія
падає посередині, стан автоматично відкочується: гра не лишається напівзмінною.

`Game` став invoker-ом: `execute(command)` веде історію, `undo()` скасовує останню дію (LIFO).
Старі методи `basic_attack`, `heal`, `use_ability`, `equip_item` лишилися з тими самими
сигнатурами, тепер вони просто створюють і виконують команду.

**CLI:** нова команда `undo`.

### Observer — `EventPublisher`, `GameObserver`, події `ActionPerformed / ActionUndone / StatusReported`
Раніше `Game` сам викликав displayer, і будь-яка нова реакція на дію вимагала б правок у `Game`.
Тепер `Game` лише публікує подію й не знає, хто слухає:
- `DisplayObserver` — показує повідомлення, тобто робить те, що раніше робив `Game`
  (тексти повідомлень не змінились);
- `CombatStatistics` — рахує урон і лікування кожного персонажа й віднімає їх при `undo`.

**CLI:** нова команда `stats`. Статистика підписується в `build_characters_registry` (тепер — у `CharactersContext`), а `Game`
для цього не змінювався.

## Текст

### Iterator — `DepthFirstIterator`, `ContainerElement.walk()`
Обхід дерева «в порядку читання» був написаний тричі окремими рекурсивними функціями: зміст
документа, видача id у навігаторі CLI, реєстрація скопійованих піддерев. Тепер це один ітератор
за протоколом Python (`__iter__` / `__next__`): лінивий, з явним стеком замість рекурсії, видає
пари `(елемент, глибина)`. Використання: `for element, depth in root.walk(): ...`.

### Visitor — `TextElementVisitor`, `accept()` в кожному елементі
Операції, які залежать від виду елемента, але не належать самим елементам, були ланцюжками
`isinstance`. Тепер це відвідувачі:
- `SerializingVisitor` (`data/text_serializer.py`) — документ → JSON;
- `DocumentConverter` (`core/text/prototypes.py`) — перебудова документа в іншому форматі;
- `_ElementKindVisitor` (`cli/text_cli.py`) — визначення виду елемента для id.

Нова операція додається новим класом без змін у класах елементів. Пропустити вид елемента
неможливо: абстрактні методи змушують реалізувати всі п'ять. Markdown/HTML-варіанти успадковують
`accept()`, тому обробляються за роллю.

## Нові тести — `tests/test_behavioral_patterns.py` (32)

- **Template Method:** нова здібність лише через хуки; перевірка цілі; жоден підклас не
  перевизначає `use()`.
- **Memento:** повне відновлення стану; знімок нічого не показує назовні; знімок не залежить
  від пізніших змін.
- **Command:** скасування кожного типу команди; зміни здоров'я; заборона повторного запуску;
  відкат дії, що впала посередині.
- **Game:** `undo` (LIFO, повідомлення, порожня історія); невдала дія не потрапляє в історію.
- **Observer:** типи й порядок подій; відписка; повторна підписка ігнорується; статистика
  разом з `undo`.
- **Iterator:** порядок обходу з глибинами; протокол ітератора; обхід з середини дерева.
- **Visitor:** розподіл за видом (зокрема HTML-варіанти); неповний відвідувач не створюється;
  вивід серіалізатора.
- **CLI:** команди `undo` і `stats`.

Запуск: `python3 -m pytest -v`.
